## 1. Arquitetura de identidade e autenticação

### 1.1 Supabase Auth
- **Arquivo:** `src/lib/supabase/client.ts`, `src/app/providers/AuthProvider.tsx`
- **Comportamento:** Usa `supabase.auth.signInWithPassword`, `getSession`, `onAuthStateChange`, `signOut`, `updateUser`. CONFIRMADO.

### 1.2 Modelo de usuário autenticado
- **Arquivo:** `src/app/providers/AuthProvider.tsx:5-15` (`AuthUser` interface)
- **Campos:** `id`, `email`, `nome`, `tenant_id`, `tenant_nome`, `papel`, `permissions`, `is_root`, `password_reset_required`.
- **Relação pessoa/tenant:** `people.id` = `auth.users.id` (mesmo UUID). Trigger `handle_new_user_create_person` cria people row automaticamente. CONFIRMADO via migration `20261009000001_tenants_and_identity.sql:51-73`.

### 1.3 Fluxos
- **Login:** `signIn` (AuthProvider:234-266) → Supabase Auth → `loadUser` → `get_current_tenant_info` RPC → `get_user_permissions` RPC → `people` select.
- **Logout:** `signOut` (AuthProvider:268-274) → `supabase.auth.signOut()`.
- **Session restore:** `useEffect` (AuthProvider:96-145) → `getSession()` → `loadUser`.
- **Password reset:** `checkPasswordReset` (AuthProvider:276-285), `requestPasswordReset` (AuthProvider:287-297) → `supabase.auth.updateUser` + `clear_password_reset_flag` RPC. Forçado via `RequireAuth` (RequireAuth.tsx:22-24).

### 1.4 Tratamento de casos especiais
- **Sem tenant ativo:** `loadUser` (AuthProvider:152-188) verifica `get_current_tenant_info`; se vazio, tenta `get_user_permissions`; se permissões existem, trata como ROOT (`admin_master`). Se não, stage `empty` com erro "Identidade não reconhecida".
- **Múltiplos vínculos:** `get_current_tenant_info` retorna apenas o primeiro (LIMIT 1, ORDER BY created_at ASC). NÃO há UI de troca de unidade/tenant no frontend. PARCIALMENTE CONFIRMADO — backend suporta múltiplos memberships, frontend não permite seleção.
- **Sem permissões:** `permsErr` tratado; se não ROOT, erro.

### 1.5 Contextos/hooks/guards
- `AuthProvider` / `useAuth` / `usePermissions` (AuthProvider.tsx:319-343).
- `RequireAuth` / `RequirePermission` (RequireAuth.tsx).
- `rbac.ts`: `isRootRole`, `hasEffectivePermission` (frontend, apenas para UI).

### 2.2 Papéis no frontend (rbac.ts)
Apenas 5 papéis "canônicos": `admin_master`, `admin_gestao`, `suporte_ti`, `suporte_master`, `suporte`. **Não inclui** os 7 papéis operacionais (admin, gestor, enfermeiro, etc.) da migration 001. DIVERGÊNCIA CONFIRMADA.

### 2.3 Permissões — divergência frontend vs backend
O frontend (`permissions/index.ts`) usa prefixo `remocao.` (ex: `remocao.remocao.read`, `remocao.admin.users.manage`). O backend (migration 001) usa prefixo `remocao.` para operacionais mas `admin.` e `support.` (sem prefixo remocao) para admin/suporte (ex: `admin.users.manage`, `support.tickets.read`). DIVERGÊNCIA CONFIRMADA — o AdminManagementPage.tsx:36-37 busca `'admin.users.manage'` e `'admin.roles.manage'` (sem prefixo remocao), mas o frontend `Perm` define `ADMIN_USERS_MANAGE = "remocao.admin.users.manage"` (com prefixo). Isso significa que o check de permissão no frontend usa keys que não existem no backend para admin/support.

### 2.4 Permissões referenciadas no código mas ausentes no catálogo backend
- Frontend `Perm` define 40 permissões com prefixo `remocao.`.
- Backend (migration 001) define 23 permissões operacionais com prefixo `remocao.` + 13 admin/support sem prefixo `remocao.`.
- Mismatch: frontend usa `remocao.admin.users.manage` mas backend tem `admin.users.manage`. frontend usa `remocao.support.tickets.read` mas backend tem `support.tickets.read`. PARCIALMENTE CONFIRMADO (código presente, mas se o banco remoto foi seeded com migration 010, as keys backend prevalecem).

### 2.5 Regras ROOT
- `admin_master` tem todas as permissões via `role_permissions` (migration 010:226-231) + `root_privileges` table.
- `has_permission()` verifica root_privileges primeiro (bypass).
- `get_user_permissions()` retorna todas as permissions se root_privileges ativo.
- Frontend `usePermissions` trata `is_root = true` como acesso total.

## 4. Escopo multi-tenant

### 4.1 Organização ativa
- Backend: `get_active_tenant_id()` (migration 002:51-79) — valida `request.active_tenant_id` contra membership; fallback para membership mais recente.
- Frontend: `AuthUser.tenant_id` (primeiro membership retornado). NÃO há UI de troca de tenant.

### 4.2 Unidade ativa
- **Não existe conceito de "unidade" separado de "tenant" no código.** O termo "unidade" aparece em `remocao_unidade` (tabela operacional, não identity). NÃO VERIFICADO se existe tabela de unidades separada de tenants.

### 4.3 Vínculos múltiplos
- Backend: `tenant_memberships` permite múltiplas memberships (unique por tenant_id+person_id, mas múltiplos tenants por person). CONFIRMADO.
- Frontend: `get_current_tenant_info` retorna apenas o primeiro membership (LIMIT 1). NÃO há seletor de contexto. PARCIALMENTE CONFIRMADO.

### 4.4 Escopo de indicadores do gestor
- Frontend: `DASHBOARD_VISUALIZAR` permission. Backend RLS em `remocao` (tabela) filtra por `tenant_id = get_active_tenant_id()` (assumido, não verificado remotamente). NÃO VERIFICADO remotamente.

### 4.5 Troca de contexto
- Backend: `set_active_tenant(p_tenant_id)` RPC existe (migration 010:760-799), com ROOT bypass. Frontend: `OrganizationSwitcher.tsx` existe mas não está claro se é usado. PARCIALMENTE CONFIRMADO.

## 5. Auditoria de operações de cadastro

### 5.1 AdminManagementPage
- **Arquivo:** `src/modules/remocao/pages/AdminManagementPage.tsx`
- **Permissão:** `admin.users.manage` ou `admin.roles.manage` (sem prefixo remocao — DIVERGÊNCIA com frontend Perm).
- **Operações:** Aprovar membership (`approve_membership` RPC), listar memberships, listar roles, listar tenants.
- **Não permite:** criar/editar/deletar usuários, atribuir roles diretamente, convidar usuários. Apenas aprovação de memberships pendentes.

### 5.2 Cadastro de usuários
- **Não existe fluxo de cadastro de usuários operacionais no frontend.** O `invite_user_to_tenant` RPC existe no backend (migration 010:640-700) mas não é chamado pelo frontend. PARCIALMENTE CONFIRMADO.
- **Criação de conta Auth:** Automática via trigger `handle_new_user_create_person` (migration 001:51-73). Separada da concessão de acesso (membership). CONFIRMADO.

### 5.3 Gestor pode cadastrar operacionais?
- **Não há evidência de fluxo de cadastro de usuários pelo gestor.** O `invite_user_to_tenant` requer `admin.users.manage` (migration 010:657). Gestor não tem essa permissão (migration 001:214-228 — gestor tem apenas operacionais + dashboard). CONFIRMADO que gestor NÃO pode cadastrar usuários atualmente.

### 5.4 TI local possui operações indevidas?
- `suporte_ti` tem `support.*` + `remocao.auditoria.read` + `remocao.dashboard.read`. NÃO tem `remocao.remocao.*` operacionais. CONFIRMADO que TI local não gerencia remoções.

### 5.5 Atribuição de papel valida org/unidade?
- `invite_user_to_tenant` verifica `has_permission('admin.users.manage')` e `is_tenant_member(p_tenant_id)`. Impede `admin_master` para não-ROOT. CONFIRMADO.

### 5.6 Criação de conta Auth separada da concessão de acesso?
- Sim. Trigger cria `people` row automaticamente. Membership é criada separadamente via `invite_user_to_tenant` ou manual. CONFIRMADO.

## 7. Lacunas, conflitos e riscos

1. **Divergência de permission keys (frontend vs backend):** Frontend usa prefixo `remocao.` para admin/support; backend não. AdminManagementPage usa keys sem prefixo. RISCO ALTO.
2. **Papéis operacionais ausentes no frontend rbac.ts:** `admin`, `gestor`, `enfermeiro`, etc. não estão em `CanonicalRole`. RISCO MÉDIO.
3. **Sem UI de cadastro de usuários:** `invite_user_to_tenant` existe no backend mas não é chamado pelo frontend. RISCO MÉDIO.
4. **Sem seletor de tenant/unidade:** Usuário com múltiplos vínculos não pode trocar contexto. RISCO MÉDIO.
5. **`get_current_tenant_info` retorna apenas 1 membership:** LIMIT 1. RISCO MÉDIO.
6. **Permissões do frontend `Permissoes` record usa keys com prefixo `remocao.` que podem não existir no backend.** RISCO ALTO.
7. **`AdminManagementPage` verifica `admin.users.manage` e `admin.roles.manage` (sem prefixo) mas frontend `Perm` define com prefixo `remocao.`.** A verificação `permissions.includes('admin.users.manage' as PermissionKey)` nunca será true se o backend retorna `admin.users.manage` sem prefixo remocao — espera, o backend retorna `admin.users.manage` (sem prefixo), e o frontend busca `'admin.users.manage'` (sem prefixo). Então funciona para admin. Mas para operacionais, o frontend busca `remocao.admin.users.manage` que não existe no backend. RISCO MÉDIO.
