## 3. Divergências conhecidas (frontend vs backend)

| Item | Frontend (`permissions/index.ts`) | Backend (migration 001/010) | Impacto |
|------|-----------------------------------|----------------------------|---------|
| Prefixo admin/support | `remocao.admin.users.manage` | `admin.users.manage` (sem `remocao.`) | AdminManagementPage verifica `admin.users.manage` (sem prefixo) — funciona para admin. Operacionais com prefixo `remocao.` podem não existir no backend. |
| Papéis operacionais no frontend | Apenas 5 em `CanonicalRole` (`admin_master`, `admin_gestao`, `suporte_ti`, `suporte_master`, `suporte`) | 12 papéis na migration 001/010 (`admin`, `gestor`, `enfermeiro_chefe`, `enfermeiro`, `medico`, `motorista`, `atendente`, `admin_master`, `admin_gestao`, `suporte_ti`, `suporte_master`, `suporte`) | `gestor`, `motorista`, `enfermeiro`, `medico`, `atendente` não estão em `CanonicalRole` do frontend. |
| `invite_user_to_tenant` | Não chamado pelo frontend | Existe no backend (migration 010:640-700) | Sem UI de convite/cadastro de usuários operacionais. |
| Seletor de tenant/unidade | Não existe no frontend | `tenant_memberships` suporta múltiplos; `get_current_tenant_info` retorna LIMIT 1 | Usuário com múltiplos vínculos não pode trocar contexto. |

## 4. Lacunas reais (sem permissão ou papel existente)

| Lacuna | Descrição | Requer novo papel/permissão? |
|--------|-----------|------------------------------|
| Gestor cadastra usuários operacionais | Gestor não tem `admin.users.manage`; não existe UI de cadastro | Sim — ou delegar via permissão específica no escopo da unidade |
| Usuário em múltiplas unidades | Frontend não permite seleção de contexto; `get_current_tenant_info` LIMIT 1 | Não — ajuste de UI e chamada de RPC existente |
| Papéis operacionais no frontend | `gestor`, `motorista`, `enfermeiro`, `medico`, `atendente` ausentes de `CanonicalRole` | Sim — adicionar ao `CanonicalRole` (mapeamento para papéis existentes no banco) |
| Prefixo de permissão admin/support | Mismatch entre frontend (`remocao.admin.*`) e backend (`admin.*`) | Não — corrigir chaves no frontend para corresponder ao backend, ou confirmar que o backend aceita ambos |

## 5. Testes necessários (positivos e negativos)

### Positivos
- Usuário com `remocao.dashboard.visualizar` acessa `/` e vê dashboard do próprio tenant.
- Usuário com `remocao.motorista.checkin` acessa `/driver/:id` e realiza check-in.
- Usuário com `remocao.admin.users.manage` acessa `/admin` e vê AdminManagementPage.
- Usuário sem permissão acessa rota protegida e vê `FeedbackPage` variant `forbidden`.
- Usuário não autenticado acessa rota protegida e é redirecionado para `/login`.

### Negativos
- Usuário sem `remocao.admin.users.manage` acessa `/admin` → `forbidden`.
- Usuário de tenant A tenta acessar remoção do tenant B → backend RLS deve bloquear (não testável localmente sem acesso remoto).
- Gestor tenta atribuir `admin_master` a outro usuário → não permitido por regras de negócio.
- Usuário com múltiplos memberships não vê unidades às quais não está vinculado.
