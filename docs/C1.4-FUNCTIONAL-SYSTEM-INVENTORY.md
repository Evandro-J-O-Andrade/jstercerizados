## 5. Fluxo de autenticação atual

Fonte: `src/contexts/AuthContext.tsx`, `src/App.tsx`

```
LOGIN
→ resolvePostLoginDestination()
→ /primeiro-acesso/senha se must_change_password = true
→ /auth/terms se termos pendentes
→ /auth/welcome
→ /dashboard
```

### Estado atual

- `changePassword()` agora usa `updateUser()` sem reautenticação.
- `resolvePostLoginDestination()` **não** pula `/auth/welcome` para admin master.
- `FirstAccessRoute` só protege autenticação básica.
- `ProtectedRoute` protege roles/permissions.

### Problema conhecido pendente

Após troca de senha, o sistema está navegando para `/auth/welcome` **sem** exigir `/auth/terms`.
Isso sugere que `resolvePostLoginDestination()` está considerando termos como já aceitos, ou a fonte de aceite não está correta.

## 6. Estrutura real de termos/consentimento

### 6.1 Tabelas encontradas

| Tabela              | Colunas principais                                                                                                                                                               | Finalidade                         |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| `first_login_state` | `person_id`, `terms_version`, `privacy_version`, `lgpd_consent_version`, `first_login_completed`, `must_change_password`, `welcome_completed_at`                                 | Proxy de estado de primeiro acesso |
| `legal_acceptances` | `id`, `person_id`, `tenant_id`, `document_type`, `document_version`, `accepted_at`, `ip`, `user_agent`, `metadata`                                                               | Aceites legais registrados         |
| `consents`          | `id`, `tenant_id`, `person_id`, `purpose`, `granted`, `channel`, `evidence_url`, `term_version`, `granted_at`, `revoked_at`, `actor_person_id`, `correlation_id`, `causation_id` | Consentimentos LGPD                |

### 6.2 Análise

`legal_acceptances` é a estrutura canônica de aceite.
`first_login_state.terms_version` funciona como cache/indicator.
O fluxo deve consultar `legal_acceptances` antes de considerar termos aceitos.

### 6.3 Fluxo correto

```
LOGIN
 ↓
must_change_password?
 ├─ SIM → /primeiro-acesso/senha
 │       ↓
 │    senha alterada
 │       ↓
 │    must_change_password = false
 │       ↓
 └─ NÃO
      ↓
legal_acceptances existe para document_type = 'terms'?
 ├─ NÃO → /auth/terms
 │       ↓
 │    aceite registrado em legal_acceptances
 │       ↓
 └─ SIM
      ↓
/auth/welcome
 ↓
"Acessar minha área"
 ↓
/dashboard
```

### 6.4 Problema atual

Após troca de senha, o sistema está navegando para `/auth/welcome` **sem** exigir `/auth/terms`.
Isso sugere que `resolvePostLoginDestination()` está considerando termos como já aceitos.

### 6.5 Correção necessária

`resolvePostLoginDestination()` deve verificar `legal_acceptances` antes de considerar termos aceitos.
`first_login_state.terms_version` não é suficiente para determinar aceite.

## 10. Análise detalhada das tabelas de termos/consentimento

### 10.1 `first_login_state`

```sql
person_id               uuid
must_change_password    boolean
terms_version           text
privacy_version         text
lgpd_consent_version    text
first_login_completed   boolean
created_at              timestamptz
updated_at              timestamptz
welcome_completed_at    timestamptz
```

**Uso atual:** Controla estado do primeiro acesso e troca de senha.

**Problema:** Não é a fonte canônica de aceite de termos.
É um cache/indicator que pode ficar desatualizado.

### 10.2 `legal_acceptances`

```sql
id                  uuid
person_id           uuid
tenant_id           uuid
document_type       text
document_version    text
accepted_at         timestamptz
ip                  text
user_agent          text
metadata            jsonb
actor_person_id     uuid
correlation_id      uuid
causation_id        uuid
```

**Uso correto:** Fonte canônica de aceite de termos/privacidade/LGPD.

**Vantagens:**

- Registra data/hora do aceite
- Registra IP e user-agent
- Permite auditoria
- Permite múltiplos aceites por pessoa (diferentes versões)
- Permite revogação futura

- **Não remover** a dashboard atual.

## 15. Estrutura de dados necessária para dashboards

### 15.1 Queries por card

**Total de tenants:**

```sql
SELECT count(*) FROM public.tenants
```

**Tenants ativos:**

```sql
SELECT count(*) FROM public.tenants WHERE status = 'active'
```

**Usuários por tenant:**

```sql
SELECT t.name, count(*) FROM public.tenants t
JOIN public.tenant_memberships tm ON tm.tenant_id = t.id
GROUP BY t.id
```

**Empresas totais:**

```sql
SELECT count(*) FROM public.companies
```

**Empresas ativas:**

```sql
SELECT count(*) FROM public.companies WHERE status = 'active'
```

**Vagas abertas:**

```sql
SELECT count(*) FROM public.jobs WHERE status = 'open'
```

**Candidatos ativos:**

```sql
SELECT count(*) FROM public.candidates WHERE status = 'active'
```

**Chamados abertos:**

```sql
SELECT count(*) FROM public.support_tickets WHERE status = 'open'
```

### 15.2 Agregações por período

**Receita do mês:**

```sql
SELECT sum(amount) FROM public.financial_transactions
WHERE type = 'income'
AND date >= date_trunc('month', current_date)
```

**Despesas do mês:**

```sql
SELECT sum(amount) FROM public.financial_transactions
WHERE type = 'expense'
AND date >= date_trunc('month', current_date)
```

**Movimentações do mês:**

```sql
SELECT count(*) FROM public.stock_movements
WHERE created_at >= date_trunc('month', current_date)
```

### 15.3 Funis

**Funil de recrutamento:**

```sql
SELECT
  count(*) FILTER (WHERE status = 'open') as vagas_abertas,
  count(*) FILTER (WHERE status = 'applied') as candidaturas,
  count(*) FILTER (WHERE status = 'interview') as entrevistas,
  count(*) FILTER (WHERE status = 'approved') as aprovados,
  count(*) FILTER (WHERE status = 'hired') as contratados
FROM public.applications
WHERE created_at >= now() - interval '30 days'
```

## 17. RLS Policies — Análise

### 17.1 Padrão observado

Todas as tabelas seguem o padrão:

```sql
CREATE POLICY table_name_member_read ON public.table_name
  FOR SELECT USING (is_tenant_member(tenant_id));

CREATE POLICY table_name_member_update ON public.table_name
  FOR UPDATE USING (is_tenant_member(tenant_id))
  WITH CHECK (is_tenant_member(tenant_id));

CREATE POLICY table_name_member_write ON public.table_name
  FOR INSERT WITH CHECK (is_tenant_member(tenant_id));
```

### 17.2 Exceções

- `tenant_memberships`: permite `is_admin_master() OR is_tenant_member(tenant_id)`
- `tenant_settings`: permite `is_admin_master() OR is_tenant_member(tenant_id)`
- Tabelas com FK: usam `EXISTS` para verificar tenant_id na tabela pai

### 17.3 Implicações

- RLS está corretamente configurado para multi-tenant.
- Qualquer query deve incluir `tenant_id` no filtro.
- O frontend deve usar `getSupabaseClient()` que injeta o tenant_id automaticamente.
