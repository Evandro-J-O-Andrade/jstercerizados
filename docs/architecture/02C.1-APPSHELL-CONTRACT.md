## 1. AppShell global

O AppShell é a camada estrutural permanente. **Não contém regra de negócio.**

```text
┌───────────────────────────────────────────────────────────┐
│ PortalHeader (fixo, topo)                                 │
├──────────────┬────────────────────────────────────────────┤
│              │  Breadcrumbs                              │
│ PortalSidebar│  PageHeader (título + ações)              │
│ (global,     │  ──────────────────────────────────────    │
│  contextual) │  ContentBoundary                          │
│              │    Loading | Error | Empty | ModuleContent │
├──────────────┴────────────────────────────────────────────┤
│ PortalFooter (fino)                                       │
└───────────────────────────────────────────────────────────┘
```

Composição atual em `src/components/portal/PortalShell.tsx`:

- `:34` — `h-dvh w-full flex-col overflow-hidden` (viewport containment)
- `:18-26` — trava `body`/`html` overflow durante a montagem do shell
- `:48` — `flex flex-col min-h-0 flex-1 overflow-hidden` (coluna central)
- `:50` — `flex flex-1 min-h-0 overflow-y-auto` (área de scroll do conteúdo)

**Princípio:** header, sidebar e footer **não são remontados** quando o conteúdo interno muda. Apenas `Outlet` troca.

## 2. Scroll containment

### 2.1 Contrato

```css
AppShell {
  height: 100dvh;
  display: flex;
  flex-direction: column;
}
Header {
  flex-shrink: 0;
}
Body {
  flex: 1;
  min-height: 0;
}
Sidebar {
  flex-shrink: 0;
}
Main {
  overflow: hidden;
}
Content {
  overflow-y: auto;
}
Footer {
  flex-shrink: 0;
}
```

### 2.2 Regras

1. A viewport é `100dvh`. O `body` **não** rola junto com o dashboard.
2. Header e footer não são deslocados por conteúdo longo.
3. O elemento que rola é **apenas** a área de conteúdo.
4. Uma tabela com 10.000 registros rola dentro do content; header, sidebar e footer permanecem.
5. Rollback visual: em falha de requisição, o conteúdo anterior permanece visível com aviso contextual — nunca tela branca nem loader global infinito.
6. Scroll horizontal acidental deve ser evitado; tabelas largas usam `overflow-x` **local**, nunca no shell.

### 2.3 Estado atual

✅ **Já implementado** em `PortalShell.tsx:34,48,50` + trava de `body/html` em `:18-26`.

⚠️ **Pendência conhecida (não pertence a este checkpoint):** `src/components/portal/PortalSidebar.tsx:266` usa
`fixed top-0 left-0 z-40 h-full transform` **sem `lg:`**, causando transbordo horizontal no desktop. Bug pré-existente, não introduzido pelo 02A.

## 3. Sidebar

### 3.1 Dois estados

| Estado    | Largura atual | Comportamento                            |
| --------- | ------------- | ---------------------------------------- |
| Expandida | `w-72`        | Rótulos + ícones + subárvore de features |
| Compacta  | `w-16`        | Ícones apenas                            |

Evidência: `PortalSidebar.tsx:254` — `const sidebarWidth = collapsed ? 'w-16' : 'w-72';`, com estado em `:109` (`:112` para `collapsedNodes`).

### 3.2 Regras

1. O sidebar pertence à **Shell**, não a um módulo. Nenhum módulo define seu próprio sidebar global.
2. O sidebar **contextual** (`ModuleSidebar`) pertence ao módulo e é fornecido pelo módulo.
3. Recolher o sidebar altera a largura do content **automaticamente** — nenhuma tela calcula largura manualmente.
4. Nenhuma tela pode definir `max-width` estrutural arbitrário próprio.
5. A navegação é derivada de `ModuleRegistry` filtrada por permissão efetiva (ver `PORTAL-ARCHITECTURE-RULES.md` §1 e §5).
6. Ícones fazem parte do design system (Lucide). **Sem emoji.**
7. Identidade visual por módulo é permitida como _accent_ (ícone, estado ativo, badge), **não** comoScheme livre. Enterprise primeiro; cor como identificador semântico, não decoração.

### 3.3 Estado atual

- ✅ Estado colapsado já existe (`w-16` / `w-72`).
- ✅ Navegação contextual por módulo já existe via `ModuleSidebar` + `ModuleRegistry`.
- 🔲 **GAP:** accent visual por módulo não está padronizado.
- 🔲 **GAP:** regra "nenhuma tela define max-width próprio" **não é verificada** — hoje é convenção, não constraint.

## 4. ContentBoundary

Quatro estados mutuamente exclusivos para qualquer região assíncrona.

| Estado                      | Contrato                                                                     |

## 5. Estratégia de loading — 3 níveis

| Nível                 | Quando                                                     | Onde                | Componente        |
| --------------------- | ---------------------------------------------------------- | ------------------- | ----------------- |
| **1 — Aplicação**     | bootstrap, autenticação, recuperação de sessão, erro fatal | tela cheia          | loader J&S global |
| **2 — Content Shell** | troca de contexto/módulo com dados pesados                 | só dentro de `main` | `SectionLoader`   |
| **3 — Local**         | salvar, excluir, recarregar tabela                         | botão/linha/região  | `InlineLoader`    |

### 5.1 Regras

1. **Nenhuma operação local destrói o shell.** Header, sidebar, breadcrumbs, perfil e footer permanecem.
2. Formulário que carrega lookups (departamentos, cargos, cidades) **permanece montado**; apenas os campos dependentes mostram estado local.
3. Nunca trocar para loader global por uma operação que afeta uma região.
4. Nível 1 é raro. Uso indevido de loader global é um defeito de UX, não uma escolha de implementação.

## 6. Preservação de estado

Estratégia desejada: **stale-while-revalidate**.

```text
cache encontrado → mostra imediatamente → revalida em segundo plano → atualiza só se mudou
```

### 6.1 Regras

1. Cache com revalidação silenciosa quando aplicável.
2. Em falha, preservar o conteúdo anterior e exibir aviso + retry contextual.
3. Nunca tela branca nem loader global infinito por falha de requisição.
4. Retry no nível da região que falhou, não da aplicação.

### 6.2 GAP

🔴 **Nenhuma biblioteca de cache instalada.** `package.json` não contém `@tanstack/react-query` nem `swr`.

| Opção                                     | Estado                                                 |

| Cache manual em `AuthContext`/repositório | Menor escopo, sem garantia de invalidação.             |
| Manter sem cache                          | Mantém o GAP de UX e de requisições.                   |

**Não decidido.** Este checkpoint não implementa cache.

## 7. Fault containment

### 7.1 Regra

> Um módulo não pode depender da implementação interna de outro módulo para funcionar.

### 7.2 Regras

1. **Espinha dorsal compartilhada**: AppShell, Header, Sidebar, ContentBoundary, breadcrumb, RBAC, contexto de módulo.
2. **Módulos independentes**: RH, Empresas, Operações, Estoque, Financeiro, Sistema.
3. Falha de RH **não** deve impedir Empresas/Financeiro de abrir.
4. Dependência entre módulos é permitida **apenas** via camadas globais/contratos compartilhados.
5. Import direto de `pages/` de outro módulo é violação.

## 9. Metro / Windows 8 — aplicação restrita

O padrão **Metro / Bento / Grid é destinado a**:

- launcher (`/dashboard`);
- dashboards gerenciais/analíticos (`/dashboard/{module}`).

**Não** aplicar automaticamente a:

- CRUDs, listas operacionais;
- formulários;
- telas de detalhe operacional.

**Enterprise primeiro; neon como acento.** Uma tela nova deve parecer parte do mesmo produto. Não pode existir um layout por módulo.

### 10.1 Persistência já existente

O banco **já possui** a persistência do builder. **Não criar tabelas novas.**

| Tabela              | Colunas | RLS   | Policies | Isolamento                                              |
| ------------------- | ------- | ----- | -------- | ------------------------------------------------------- |
| `dashboard_layouts` | 10      | ativa | 3        | `is_tenant_member(tenant_id)` em `USING` e `WITH CHECK` |
| `dashboard_widgets` | 7       | ativa | 3        | `is_tenant_member(tenant_id)` em `USING` e `WITH CHECK` |

Políticas presentes em ambas: `*_member_read` (SELECT), `*_member_update` (UPDATE), `*_member_write` (INSERT), todas com `roles = {public}` e isolamento por `is_tenant_member(tenant_id)`.

### 10.2 Divisão catálogo vs layout

| Camada                          | Persistência                              | Justificativa                          |
| ------------------------------- | ----------------------------------------- | -------------------------------------- |
| **Catálogo de tipos de widget** | código                                    | muda com deploy, não é dado de usuário |
| **Layout por tenant/usuário**   | `dashboard_layouts` + `dashboard_widgets` | dado de usuário, precisa de RLS        |

### 10.3 GAP principal

🔴 **As duas tabelas estão prontas e RLS-corretas, e não têm nenhum consumidor no frontend.**

- `dashboard_layouts` → 0 consumidores
- `dashboard_widgets` → 0 consumidores
- `MetroTiles.tsx` usa grid, mas **não referencia** nenhuma das duas.

O caminho não é projetar o engine: é **conectar `MetroTiles` às tabelas existentes**, respeitando RBAC/RLS.

### 10.4 Regra de autorização do builder

> Adicionar um widget **não** pode conceder acesso a dados.

```text
AuthUser → Tenant → Role → Permission → widget permitido → query autorizada → dados
```

O Builder opera sobre um **catálogo de widgets permitidos**.

## 11. Segurança — achado separado

> **Não corrigir neste checkpoint.** Registrado para o `01E.1` (Supabase Grants / RLS Security Audit).

### 11.1 Achado

`anon` possui privilégio pleno sobre `dashboard_widgets` e `dashboard_layouts`:

```
SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER
```

A proteção hoje vem **exclusivamente** das policies RLS (`is_tenant_member(tenant_id)`), não dos privilégios.

### 11.2 Leitura correta

Este é um **achado estrutural**, não uma contagem de vulnerabilidades. O vetor real de classificação é:

```text
tabela → operação → role/grantee → policy → USING → WITH CHECK
       → tenant isolation → exposição pública → risco efetivo
```

- `PERMISSIVE` é o **default** do PostgreSQL, não um defeito.
- `roles = {public}` é normal: `public` agrega `anon` e `authenticated`; quem restringe é o `qual`.
- `TRUNCATE` e `REFERENCES` não são cobertos por RLS — precisam de classificação separada por `GRANT`.

### 11.3 Não assumir exclusividade

O padrão pode se repetir nas 221 tabelas. Se for o caso, é **estrutural**, não específico destas duas tabelas. Deve ser auditado como tal.

### 11.4 Base do `01E.1`

Levantamento já feito (read-only, `docs/supabase-inventory.json`):

- 221 tabelas, **221 com RLS ativa** (`rowsecurity = true` em todas)
- 600 policies; padrão dominante de `WITH CHECK` é `is_tenant_member(tenant_id)` (232 ocorrências)
- Tabelas filhas usam `EXISTS(... is_tenant_member(pai.tenant_id))`
- 249 policies com `WITH CHECK` nulo — provavelmente só `SELECT`, **a confirmar**
- Casos que merecem classificação: `people` (1 policy), `candidate_job_alerts` e `favorite_jobs` (`QUAL` sem checagem de tenant)

**Conclusão preliminar:** o RLS está **estruturalmente bem implementado**. A premissa inicial de "201 tabelas com policies permissivas" **não sobrevive à inspeção** — era artefato de leitura (`PERMISSIVE` = default). Isso **rebaixa** a prioridade do `01E.1` frente a `01E.2` e `01E.3`.
