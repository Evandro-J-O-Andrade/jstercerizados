## 0. Objetivo

Estabelecer **uma única fonte canônica** para a autorização no frontend, eliminando a dupla leitura de permissões entre `PermissionGuard` e `PortalSidebar`/`ModuleSidebar`, e remover o bypass de `admin_master`.

**Não toca no Supabase.** Nenhuma migration, `GRANT`, `REVOKE` ou alteração de policies.

### 1.2 Dupla leitura no sidebar

```tsx

permissions,  // vindo de useAccount() → AccountContext.tsx:152

// ModuleSidebar.tsx — não recebe permissions como prop
// PortalSidebar.tsx:106-107

```

**AccountContext.tsx:152**: `activePermissions: permissions` — **é a mesma referência** de `AuthContext.tsx:302`, apenas repassada. Não há duplicação de dados, apenas dupla camada de contexto.

### 1.3 Bypass do `admin_master`

```tsx
// PermissionGuard.tsx:75-77
if (isAdminMaster) {
  return <>{children}</>;
}
```

**NÃO é um bypass de segurança do backend.** O Supabase ainda aplica RLS. É um **curto-circuito frontend** que pode esconder páginas de usuários que não deveriam ver.

### 1.4 `admin_master` possui permissões reais

```tsx
// AuthContext.tsx:268-282
if (adminMaster) {
  const { data: allPerms } = await supabase.from('permissions').select('*');
  permissionsData = normalizePermissions(allPerms || []);
}
```

`admin_master` carrega **todas as permutações do Supabase** no estado `permissions`. O bypass de `PermissionGuard` é **arquiteturalmente redundante**.

## 2. Contrato proposto

### 2.1 Fonte única de autorização

```text
AuthContext (useAuth)
      │
      ├── permissions[]           ← fonte canônica
      ├── hasPermission(key)      ← verificação canônica
      ├── hasAnyPermission(keys)  ← verificação canônica
      └── hasAllPermissions(keys) ← verificação canônica
```

**Regra:** Todo componente que verifica autorização deve usar `useAuth().permissions` + `utils/rbac`.

**Não:** `AccountContext.permissions` como alternativa paralela.
**Não:** `PermissionGuard` com bypass.

### 2.2 Permissão como string canônica

Formato: `resource.action` (ex: `people.read`, `candidates.create`, `finance.dashboard.read`).

Derivado de:

```ts
getPermissionKey(permission: Permission): string
  → permission.name || `${permission.resource}.${permission.action}`
```

Verificado em `utils/rbac-normalize.ts:41-49`.

### 2.3 ModuleContext não faz autorização

```tsx
// ModuleContext.tsx:15-18
interface ModuleContextType {
  currentModule: ModuleDefinition | null;
  currentFeature: ModuleFeature | null;
  isModuleLauncher: boolean;
}
```

ModuleContext resolve **contexto de navegação** (qual módulo/feature está ativo), **não** verifica permissões. Filtra acontece no consumidor (PortalSidebar, ModuleSidebar) usando `useAuth().permissions`.

## 3. Mudanças propostas (P1.6-A)

### 3.1 Remover bypass do `admin_master` em PermissionGuard

**Antes:**

```tsx
if (isAdminMaster) {
  return <>{children}</>;
}
```

**Depois:**

```tsx
// admin_master já possui todas as permissions no estado
// a verificação normal aplicará-se automaticamente
```

**Impacto esperado:** Zero — `admin_master` carrega todas as permissions, então o `hasPermission` retornará `true` para tudo.

### 3.2 Unificar consumo de permissions

```tsx
// PortalSidebar.tsx — MUDANÇA
const { permissions } = useAuth(); // ← em vez de useAccount()
// OU
import { useAuth } from '@/contexts/AuthContext';
// usar useAuth() para permissions, useAccount() para identity
```

A regra:

```text
permissions → useAuth()  (fonte canônica)
identity → useAccount()  (layer de presentation)
currentModule/feature → ModuleContext
```

### 3.3 Não alterar AccountContext

```tsx
// AccountContext.tsx:152
activePermissions: permissions,  // mantido como pass-through
```

AccountContext continua expondo `permissions` por conveniência, mas:

- **`activePermissions` deve ser documentado como "pass-through de useAuth"**
- Novos consumidores devem preferir `useAuth().permissions` diretamente

## 4. Decisões adotadas

| Decisão                                   | Motivo                                             | Documentação |
| ----------------------------------------- | -------------------------------------------------- | ------------ |
| `AuthContext` é fonte canônica            | É quem carrega o estado real carregado do Supabase | §2.1         |
| `admin_master` usa permissions reais      | `AuthContext.tsx:268-282` já carrega todas         | §1.4, §3.1   |
| PermissionGuard não deve bypassar         | Redundante e pode esconder inconsistências         | §3.1         |
| AccountContext.permissions é pass-through | Não há duplicação de dados, apenas dupla camada    | §1.2         |
| ModuleContext não faz autorização         | Separação de responsabilidade clara                | §2.3         |
