## 3. Mecanismo real de rotas (verificado em `src/App.tsx`)

Documentado aqui para não repetir a pesquisa.

### 3.1 Três mecanismos coexistindo

| #   | Mecanismo                                                               | Local                                | Qtd                |
| --- | ----------------------------------------------------------------------- | ------------------------------------ | ------------------ |
| 1   | `launcherRoutes` derivado de `PORTAL_MODULES` + `MODULE_PERMISSION_MAP` | `App.tsx:187-198`; render `:738-765` | 28 rotas de módulo |
| 2   | `<Route>` escritos à mão, cada um com `<PermissionGuard>`               | `App.tsx:236-737`                    | 106 rotas          |
| 3   | Catch-all `"Em breve"` como rota filha de (1)                           | `App.tsx:751-762`                    | 1 por módulo       |

Estrutura do módulo gerado:

```tsx
const ModuleLauncher = createModuleDashboardPage(route.moduleId);
<Route path={route.path} element={<PermissionGuard permission={route.permission}><ModuleLauncher /></PermissionGuard>}>
  <Route index element={null} />
  <Route path="*" element={<EmptyState title="Em breve" ... icon={Clock} />} />
</Route>
```

### 3.2 Conflito: 22 de 28 módulos têm rota de hub declarada duas vezes

As 22 rotas de módulo que existem **tanto** explicitamente em `App.tsx` **quanto** via `launcherRoutes`:

`almoxarifado`, `assinaturas`, `auditoria`, `configuracoes`, `configuracoes/seguranca`, `contabilidade`, `crm`, `estoque`, `faturamento`, `financeiro`, `fiscal`, `gestao-saas`, `global`, `ia`, `integracoes`, `onboarding`, `relatorios`, `rh`, `roles-permissoes`, `servicos`, `suporte`, `tenants`

As rotas explícitas são declaradas primeiro (236-737); as geradas depois (738-765). Para paths idênticos, a **primeira declaração prevalece**, portanto a rota explícita sombreia a gerada.

**Efeito verificado no código:** o hub desses módulos renderiza a página escrita à mão, não `ModuleDashboardPage`.

| Módulo    | Rota explícita | Elemento                                   |
| --------- | -------------- | ------------------------------------------ |
| `rh`      | `App.tsx:271`  | `<RHDashboardPage />` sob `people.read`    |
| `estoque` | `App.tsx:615`  | `<Estoque />` sob `stock.dashboard.read`   |
| `suporte` | `App.tsx:639`  | `<Suporte />` sob `support.dashboard.read` |

O catch-all `"Em breve"` permanece alcançável para **sub-rotas** não declaradas, porque a rota explícita do hub não tem filhos.

**Classificação: `DECISÃO PENDENTE`.** Consolidar em um mecanismo único é mudança de código — **não executada**.

### 3.3 Rotas de feature

`PORTAL_MODULES` declara **102 feature routes** (indentação 8). **50 delas** também estão escritas à mão em `App.tsx`. As demais são resolvidas pelo catch-all `"Em breve"` do módulo — ou seja, **features registradas no Registry podem não ter implementação de tela** e cair no "Em breve" sem distinção visual entre "em dev" e "não implementada".

### 5.1 Risco

A arquitetura desejada é `metadata + identity + route + permissions + entrypoint` no Registry, com os detalhes internos pertencendo a cada módulo. Um Registry de 2479 linhas que declara 72 `actions` e 102 feature routes está próximo de conhecer os detalhes internos de cada módulo — o risco é tornar-se o _mega-registry_ que a arquitetura quer evitar.

### 5.2 Nota

**Isto NÃO é um argumento por refatorar agora.** 2479 linhas não é, por si só, um defeito, e a concentração pode ser intencional. É um sinal a investigar, com checkpoint próprio, depois do AppShell.

## 10. Correção: MODULE_PERMISSION_MAP não está vazio

Após inspeção direta do worktree (`src/components/portal/ModuleRegistry.ts:2463-2493`), **`MODULE_PERMISSION_MAP` não está vazio para todos os módulos**. Apenas 6 de 28 módulos têm permission string vazia (não mapeada):

| Módulo            | Permission |
| ----------------- | ---------- |
| `inicio`          | `''`       |
| `servicos`        | `''`       |
| `ia`              | `''`       |
| `preferencias`    | `''`       |
| `minha-conta`     | `''`       |
| `seguranca-conta` | `''`       |

O RH (`rh: 'people.read'`) e Recrutamento (`recrutamento: 'jobs.read'`) estão corretamente mapeados. O registro anterior de "6 módulos com permission vazia" estava **parcialmente incorreto** — precisava ser "6 módulos sem permission mapeada" e não "6 módulos com MODULE_PERMISSION_MAP vazio".

### 10.1 Contrato correto de resolução

```text
Router (React Router)
   ↘
App.tsx (rotas explícitas = 106)
   ↘
PermissionGuard (useAuth → permissions)
   ↘
ModuleContext (ModuleProvider — derived de useLocation)
   ↘
PortalSidebar / ModuleSidebar (consumem ModuleContext)
   ↘
ModuleDashboardPage → getModuleById()
   ↘
Portais / páginas específicas
```

**Dono da decisão "módulo atual + feature atual":** `ModuleContext.tsx` — derivado de `useLocation()` e `PORTAL_MODULES`, não de um dispatcher central.

**Dono da decisão de permissão:** `PermissionGuard.tsx` — derivado de `useAuth().permissions`, não de `ModuleContext` ou `AccountContext`.

**Dono da decisão de account identity:** `AccountContext.tsx` — derivado de `AuthContext` (via `useAuth`) + `UserIdentity.ts`.
