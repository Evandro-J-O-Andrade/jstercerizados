
- Fazem queries diretas com `.from('tabela')`

## 5. RECONCILIAÇÃO AUTH/PRIMEIRO ACESSO

### 5.1 Estado Atual do Fluxo

```
LOGIN
 ↓
AuthContext.login()
 ↓
Carrega: people, tenant_memberships, roles, permissions, first_login_state, legal_acceptances
 ↓
resolvePostLoginDestination()
 ↓
├── must_change_password? → /primeiro-acesso/senha
├── terms pendentes? → /auth/terms
├── welcome pendente? → /auth/welcome
└── /dashboard
```

### 5.2 Componentes Implementados

### 5.3 Problemas Identificados

| Problema                                                     | Severidade | Observação                                                     |
| ------------------------------------------------------------ | ---------- | -------------------------------------------------------------- |
| `resolvePostLoginDestination()` pode pular `/auth/terms`     | Alta       | Depende de `legal_acceptances` estar carregado                 |
| `first_login_completed` não deve pular welcome               | Média      | Welcome deve aparecer em todo login                            |
| `welcome_completed_at` adicionado mas não usado corretamente | Média      | Coluna existe, lógica precisa revisão                          |
| `legal_acceptances` como fonte canônica                      | Alta       | Deve ser verificada antes de `first_login_state.terms_version` |

### 12.2 Comportamento esperado

```text
                 NAVEGADOR
                    │
          ┌─────────┴─────────┐
          │                   │
       F5/reload          fechar navegador
          │                   │
          ▼                   ▼
    RESTAURAR SESSION       DESCARTAR
          │                   │
          ▼                   ▼
     continua logado      novo LOGIN
```

### 12.3 Restrições

- ❌ Não utilizar `sessionStorage` puro (não resolve reload)
- ❌ Não utilizar `persistSession: false` (quebra reload)
- ❌ Não realizar logout em `beforeunload`
- ❌ Não remover a sessão em reload
- ❌ Não implementar timeout de inatividade
- ❌ Não armazenar senha no navegador
- ❌ Não alterar dashboard, sidebar, páginas ou site público
- ❌ Não criar migration
- ❌ Não alterar banco

### 12.4 Implementação futura

Distinguir claramente:

```text
PAGE RELOAD
    ≠
BROWSER SESSION TERMINATION
```

O access token/refresh token deve permanecer sob gerenciamento do Supabase Auth.

A implementação deverá garantir:

- Sessão sobrevive a reload/F5

- Logout manual funciona

## 13. FLUXO DE TROCA DE SENHA — REQUISITO CORRIGIDO

### 13.1 Regra

```text
SENHA ATUAL
        ↓
    referência
        ↓
NOVA SENHA
        ↓
deve ser DIFERENTE
```

### 13.2 Comportamento esperado

| Senha atual | Nova senha | Resultado                                         |
| ----------- | ---------- | ------------------------------------------------- |
| `Senha123`  | `Senha123` | ❌ rejeitar — nova senha deve ser diferente       |
| `Senha123`  | `Senha456` | ✅ alterar                                        |
| `Senha123`  | `Senha456` | confirmação `Senha456` → ✅ alterar               |
| `Senha123`  | `Senha456` | confirmação `Senha789` → ❌ confirmação diferente |

### 13.3 Implementação correta

```ts
// Validação frontend:
if (newPassword !== confirmPassword) {
  // ❌ "As senhas não coincidem"
}

// Backend/Supabase:
await supabase.auth.updateUser({ password: newPassword });

// Se Supabase retornar:
// "New password should be different from the old password."
// significa que a nova senha é igual à senha anterior.
// NÃO transformar em "as senhas não correspondem".
```

### 13.4 Observação

O formulário de primeiro acesso NÃO possui campo "senha atual".
A senha atual foi digitada no login e não está disponível no frontend.
Portanto, a única forma de detectar senha igual é via resposta do Supabase Auth.

### 13.5 Instrumentação (temporária)

Logar sem expor segredos:

```text
[AUTH:CHANGE_PASSWORD]
hasSession
userId
newPasswordLength
confirmPasswordLength
```

Nunca imprimir:

- senha atual
- nova senha
- confirmação
- access token
- refresh token
