## 0. Sumário executivo

A arquitetura-alvo **já existe como pastas vazias** no repositório. Não é desenho novo:
é esqueleto previsto que nunca foi preenchido. Isso muda a natureza do trabalho — o P1.7
não projeta, reconcilia.

Três achados que precedem qualquer decisão:

1. **Isolamento de falha é zero hoje.** `App.tsx` importa ~90 páginas de dashboard de forma
   **eager** (não lazy). Uma falha de import em qualquer módulo derruba o portal inteiro.
   O princípio "cai a cabeça, corpo continua" está escrito na arquitetura e **ausente no código**.
2. **`src/modules/rh/` não é um módulo.** São 10 arquivos, ~160 linhas, dos quais a totalidade
   são barrels de re-export. `RHDashboardPage.tsx` tem 3 linhas e re-exporta uma página de
   `pages/dashboard/`. Zero propriedade. É fachada.
3. **Dois defeitos de runtime confirmados em `App.tsx`/`PortalShell`:** `ModuleProvider`
   montado duas vezes (aninhado) e container `max-w-[1920px] px-4 py-6` aplicado duas vezes
   (padding duplo). Detalhados na seção 08.

## 02 — MASTER DISPATCHER

**Alvo:** componente único acima de todos os módulos, operando por contratos e registro —
**não** um mega-componente com milhares de `if`s.

**Estado:** `NÃO IMPLEMENTADO`. Não existe dispatcher.

O papel é desempenhado **por acidente** por `App.tsx → RoutesAndLayout()`, que é
**893 linhas** com:

- ~80 `<Route>` explícitos escritos à mão (linhas 236–737)
- um gerador de rotas (`launcherRoutes`, linhas 187–198) derivado de `PORTAL_MODULES`
- um `<Route path="*">` de fallback final (linha 766)

`launcherRoutes` é o único traço de dispatcher por contrato. Ele mapeia `PORTAL_MODULES`
para caminhos, mas **não resolve página**: `createModuleDashboardPage(route.moduleId)`
gera o mesmo launcher genérico para todo módulo.

**Problema:** o dispatcher real está partido em dois lugares —
`PORTAL_MODULES` decide _o que existe_, `App.tsx` decide _o que renderiza_, e os dois
divergem. Ver seção 06.

**Classificação:** `NÃO IMPLEMENTADO`.

## 06 — DASHBOARDS

**Alvo:** dashboard é **visão**. Não contém regra, SQL, autorização, repositório.
`Dashboard → Orchestrator → Service → Repository → Supabase`.

**Estado:** `CONFLITANTE`. Excesso de dashboard, Ausência de orquestração.

`src/pages/dashboard/` tem **90 arquivos** — a maior concentração do projeto.
`src/pages/` tem 129 no total.

### Defeito A — rota explícita mata o launcher do módulo

`FinanceiroPage` está montado em **duas rotas**:

- `App.tsx:458` → `financeiro/contas-pagar`
- `App.tsx:708` → `financeiro`

Rotas explícitas são avaliadas antes de `launcherRoutes`. Consequência: em
`/dashboard/financeiro` **nunca** renderiza o launcher do módulo financeiro —
renderiza `FinanceiroPage`, que é a tela de **contas a pagar**. O usuário que navega ao
módulo Financeiro recebe a sub-tela errada, sem menu lateral e sem breadcrumb do módulo.

O mesmo padrão vale para `rh` (explícito em `App.tsx:271`, e `rh` também existe em
`PORTAL_MODULES`): o launcher de RH é inalcançável.

**Este é o defeito de maior impacto funcional do inventário.**

### Defeito B — `shared/crud` viola a própria fronteira

Restrição registrada: `shared/crud/` não pode conhecer o portal.

`src/shared/crud/ModulePage.tsx:3` importa `useAuth` de `@/contexts/AuthContext` e
consome `currentTenantId` e `isAdminMaster`. Além disso, `isAdminMaster` **controla a UI**:

```ts
const actions = isAdminMaster ? <CrudCreateButton onClick={openCreate} /> : undefined;
```

```ts
<DataTable ... showActions={isAdminMaster} />
```

Ou seja, `shared/` carrega escopo de tenant **e** RBAC da plataforma. Não é biblioteca
reutilizável — é camada do portal com nome de biblioteca. Além disso todos os 7 arquivos
importam de `@/components/ui/*`, o que é aceitável, mas o `@/contexts` não é.

Consumidores atuais de `shared/crud`: apenas `components/modules/ModulePage.tsx`, que é
usado por `pages/dashboard/{Estoque,Servicos,Suporte}.tsx`.

**Classificação:** `CONFLITANTE`.

## 07 — SIDEBARS

**Alvo:** sidebar global + sidebar do módulo, compostas — nunca uma sidebar universal
com centenas de condições.

**Estado:** `PARCIAL` / `CONFLITANTE`.

### Defeito C — a sidebar do módulo ignora o slot `sidebar`

`ModuleWorkspace` declara e implementa o slot:

```ts
interface ModuleWorkspaceProps { ...; sidebar?: ReactNode; ... }
```

```tsx
<div className="flex min-h-0 flex-1 gap-6">
  {sidebar}
  {children}
</div>
```

Mas `ModuleDashboardPage.tsx` **não usa o slot**. Passa `ModuleSidebar` como _child_,
antes do `<div className="flex-1 min-w-0">`:

```tsx
<ModuleWorkspace title={...}>
  {!isOnDefaultRoute && (
    <ModuleSidebar module={module} permissions={activePermissions} onNavigate={() => {}} />
  )}
  <div className="flex-1 min-w-0">...</div>
</ModuleWorkspace>
```

Resultado: as duas coisas caem no flex de `children`, então **aparece** funcionando. Mas o
contrato está violado — o slot `sidebar` nunca é populado, e qualquer página que o use
receberá layout diferente das geradas pelo launcher. Isso explica a inconsistência de
sidebar observada entre páginas.

### Defeito D — a sidebar universal ainda existe

`src/components/portal/PortalSidebar.tsx` tem **23.838 bytes**. É exatamente a "sidebar
universal com 200 condições" a arquitetura-alvo proíbe. `MetroTiles.tsx` (37.035 bytes)
faz o papel análogo no portal do candidato.

**Classificação:** `CONFLITANTE` com o alvo.

**Alvo:** `Portal Runtime = Global Header + Module Sidebar + Module Workspace + Global Footer`.

### Defeito E — `ModuleProvider` montado duas vezes

```
App.tsx:229       <ModuleProvider>
App.tsx:230         <AppShell />
App.tsx:231       </ModuleProvider>

AppShell.tsx:6      <PortalShell>          → PortalShell.tsx:82  <ModuleProvider>
```

### Defeito F — container duplicado, padding duplo

```
ModuleWorkspace.tsx:32  (idêntica, como baseClasses)
```

Qualquer página que passe por `PortalShell` **e** por `ModuleWorkspace` recebe
`px-4 py-6 ... px-10` duas vezes, com `max-w` competindo. Isso é a causa provável do
`mx-auto` se comportando de forma inconsistente entre dashboards.

### Defeito G — footer duplicado por dois mecanismos

Existe `src/components/portal/PortalFooter.tsx` (2.773 bytes) **e** um footer escrito
inline em `PortalShell.tsx:56–73`. O inline é o que efetivamente renderiza. `PortalFooter.tsx`

### Comportamento de viewport

## Conclusão

O projeto tem a **forma** da arquitetura-alvo (pastas criadas, um módulo candidato
coerente, `shared/crud` inicializado) mas **não tem o isolamento** dela. Os três eixos
pedidos — `GLOBAL`, `MASTER DISPATCHER`, `ORCHESTRATORS` — estão vazios ou acidentais.

O caminho de menor risco não é mover arquivos em massa. É:

1. corrigir os **três defeitos ativos** (rota de financeiro, `ModuleProvider` duplo,
   container duplo) — são bugs, não arquitetura;
2. só então reconciliar:登记表 de propriedade por arquivo (`owner-along`, `owner-target`) como
   já definido em A8.3;
3. só então mover, na ordem de dependência da seção 12.

Nenhum item acima foi implementado. Nenhum commit foi feito.
